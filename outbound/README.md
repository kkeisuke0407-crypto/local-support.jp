# local-support.jp アウトバウンド送客エンジン（設計）

> 目的：企業へ直接アプローチし、「施設管理コスト削減の無料診断」を訴求して
> **local-support.jp の見積依頼（送客）件数を最大化する**。SEO（pull）ではなく
> アウトバウンド（push）で「既契約だが見直していない」層を掘り起こす。
>
> 最適化目標：**獲得案件数（＝見積依頼/送客数）**。収益モデル（加盟店課金）は本フェーズ対象外。

---

## 0. スコープと原則

- **MVP対象**：東京都 100社。**ただしシステムは全国・数万社規模を前提に設計**する。
- **アプローチ優先順位**：① メール送信 → ② フォーム入力 → ③ 要確認（保留）
- **human-in-the-loop**：
  - メール … 下書き生成・スコアリング・キューイングまで自動。**最終送信承認は人間**。
  - フォーム … 検出・項目解析・入力まで自動。**送信ボタンの直前で停止 → 人間確認**。
- **自動送信しない例外**：CAPTCHA / 画像認証 / SMS認証 / 「営業お断り」明記 → ステータス `要確認` で保存。
- **コンプライアンス**（後述）：特定電子メール法・個人情報保護法・robots.txt・レート制限を最初から組み込む。

```
│        │                        │                                 │
│        └──────────┬─────────────┘                                 │
│                   ▼                                               │
│  3. スコアリング Scorer  →  4. チャネル判定（email>form>hold）       │
│                   │                                               │
│                   ▼                                               │
│  5. AI下書き生成 Drafter（企業別に件名・本文を最適化）               │
│                   │                                               │
│                   ▼                                               │
│  6. 承認キュー Review Queue  ──(人間GO)──►                          │
│                   │                                               │
│        ┌──────────┴───────────┐                                  │
│        ▼ email                ▼ form                              │

│        └──────────┬───────────┘                                  │

```

### スケール設計
| 項目 | MVP（〜数百社） | 全国（数万社） |
|---|---|---|
| DB | SQLite（`crm.sqlite`） | PostgreSQL（同スキーマ・`crm.sql`をそのまま移行可能） |
| ジョブ | cron + 単一プロセス | キュー（Redis/BullMQ等）＋ワーカー水平分割 |
| 収集 | 法人番号API＋業界DPを都度取得 | 日次バッチ＋差分更新（`updated_at`で増分） |
| 送信 | 1ドメイン少量 | 複数送信アドレス＋ウォームアップ＋スロットリング |

> **重要な実装上の注意**：本エンジンはDB・サーバ・常駐ジョブを要するため、
> 静的サイト（Astro/Cloudflare Pages）とは**別ランタイム**。本リポジトリには
> 設計・スキーマのみ置き、実装は別サービス（または別リポジトリ）に切り出す前提。
> `outbound/` は `src/` `public/` の外にあるため**公開ビルドには含まれない**。

## 2. データ取得元（全国網羅・無料・合法を優先）

### 軸＝公的データベース（数万社スケールの母集団）
| 取得元 | 内容 | 用途 |
|---|---|---|
| **国税庁 法人番号システム Web-API** | 全法人の法人番号・商号・所在地（公式・無料・全件DL可） | 法人マスタの背骨。`corporate_number`採番 |
| **介護サービス情報公表システム（厚労省）** | 全国の介護事業所・運営法人・所在地 | `kaigo`セグメントの母集団 |
| **医療情報ネット（医療機能情報提供制度）/病院名簿** | 全国の病院・診療所 | `byoin`/`clinic`セグメント |
| **マンション管理業協会・賃貸管理業協会の登録業者一覧（公開）** | 登録管理会社リスト | `mansion_kanri`/`fudosan_kanri`の母集団 |

### エンリッチ＝各社公式サイト
- 公式サイトを巡回し **問い合わせメール / 問い合わせフォームURL / 電話番号 / 規模情報** を抽出。
- **必ず** `robots.txt` を尊重し、`robots_allowed=0` のサイトはスクレイピング対象外（電話のみ手動）。
- レート制限：同一ドメインへのアクセスは最低 N 秒間隔、全体QPS上限を設定。User-Agent明示。

> 取得項目の優先：**メールアドレス最優先**。メールが取れた時点で `contact_channel=email`。
> 取れなければフォームURL検出 → `form`。どちらも無ければ `hold`（要確認）。

## 3. 処理パイプライン（日次・human-in-the-loop）

1. **収集** — 公的DBから対象セグメントの法人を取得 → `companies` にUPSERT（`corporate_number`キー）
2. **エンリッチ** — 公式サイトから email / form / 電話 / 規模を補完
3. **スコアリング** — `config/scoring.ts` の `computeScore()` で 0–100点＋理由＋推奨チャネルを算出
4. **チャネル判定** — email > form > hold
5. **AI下書き生成** — 企業ごとに件名・本文を生成（コスト削減診断訴求・配信停止導線込み）
6. **承認キュー** — `outreach_messages.status='draft'` を人間がレビュー → `approved`
7. **送信**
   - email：ESP API で送信（スロットリング）→ `sent`
   - form：Playwrightで入力 → **送信前で停止** → 人間が確認して送信 → `sent`。CAPTCHA等検出時は `needs_review`（CRM `要確認`）
8. **反応取込** — ESP/受信箱のWebhookで 開封・返信・バウンス・配信停止 を `message_events` へ → `crm_status` 更新
9. **送客** — 返信・興味ありの相手を local-support.jp の見積フォーム（`/api/quote`）へ誘導 → `見積依頼`

## 4. メール送信基盤

### ドメイン・認証（到達率の生命線）
- 送信元：`partner@local-support.jp`（指定どおり）。
- **本体ドメインのレピュテーション保護のため、送信は専用サブドメイン推奨**（例 `partners.local-support.jp` / `go.local-support.jp`）。本体 `local-support.jp` のSEO・通常メールへの巻き添えを防ぐ。
- **SPF / DKIM / DMARC を必ず設定**（未設定だと大半が迷惑メール行き）。

### 送信プロバイダ（候補）
| 候補 | 向き | 備考 |
|---|---|---|
| Amazon SES | 大量・低コスト | AUP遵守前提。バウンス/苦情率の監視必須 |
| SendGrid / Mailgun | 中量・運用容易 | Webhookで開封/バウンス取得が楽 |
| 営業特化（Instantly等） | 少量・到達特化 | inbox warmup内蔵 |

### 運用ルール（迷惑メール化・ブラックリスト回避）
- **ウォームアップ**：初期は1アドレス 20〜30通/日から段階増加。
- **スロットリング**：時間あたり送信数に上限、ランダム間隔。
- **suppression list**：配信停止・ハードバウンス・苦情は即時除外（`suppression`テーブル）。
- **バウンス率/苦情率を監視**し、閾値超過で自動停止。

## 5. コンプライアンス（最初から組み込む）

### 特定電子メール法（B2Bでも必須）
- すべての営業メールに **①送信者情報（事業者名・住所・連絡先）を表示** ②**受信拒否（配信停止）の方法を明記**。
- 配信停止リクエストは即時 `suppression` 登録し、以後送信しない。

### 個人情報保護法（APPI）
- 個人名アドレス（`taro.yamada@…`）は個人情報。利用目的（営業連絡）を社内で明示・記録。
- 削除・利用停止の依頼に対応する窓口を用意。

### その他
- robots.txt 遵守、レート制限、過度なアクセス禁止（業務妨害リスク回避）。
- 「営業お断り」明記の企業は対象外（`要確認`で保存し送信しない）。

## 6. ファイル構成

```
outbound/
  README.md              ← 本ファイル（全体設計）
  config/
    scoring.ts           ← スコアリング仕様（実行可能な単一ソース）
  schema/
    leads_schema.md      ← 営業リストCSVスキーマ（エクスポート形式）
    crm.sql              ← CRM データベーススキーマ（SQLite互換／Postgres移行可）
```

### CRMステータス
`未送信 → 送信済み → 返信あり → 興味あり → 見積依頼 → 商談中 → 失注`
＋運用用：`要確認`（フォーム例外）／`配信停止`／`バウンス`
